下面为你整理**半 To C 版本（偏向个人创作者与小微企业团队）** 的知识库系统权限设计（最终版 v4）。

> **本版（v4）修订说明**（依据《../开发文档_新版如何实现/03-权限设计-新版如何实现md》对当前代码的核对结论修订 v3）：
> 1. **纠正 v3 前提**：代码中 `is_private` 默认值已是 `true`，本版核心变更修正为"补齐私有库在**列表与详情两层**的完全隐身"，无需数据迁移。
> 2. **收敛管理员边界矛盾**（v3 中 2.1 与 3.3/5.1 三处说法冲突）：统一为"admin 穿透项目权限用于管理与审计；模型**元数据**可见全量，密钥除本人外一律脱敏，不可绑定使用他人私有模型"。
> 3. **模型范围补全**：保留部门模型，形成 公有 / 部门 / 私有 三类 scope，避免照搬 v3 丢失既有能力。
> 4. **兜底链可感知、可关闭**：私有模型失效回退公共模型必须提示，并提供用户级"不回退直接报错"开关。
> 5. **明确状态码**：私有库对非成员的**读**访问返回 404（防存在性探测），成员档位不足仍 403。
> 6. **保底规则补边界**：仅统计激活用户；部门授权来源计入统计；写明与 admin 穿透的关系。

---

# 1. 总体设计

系统权限分为两层，互不耦合：

1. **全局功能权限**（菜单/按钮/接口）
   - 使用 Casbin，控制用户能"进入哪些模块、看到哪些按钮"。
2. **项目（知识库）与数据级权限**（资源归属与可见性）
   - 知识库使用 `project_member` / `project_dept` 表控制。
   - 模型配置使用 `scope`（`public` / `dept` / `user`）+ `user_id` / `dept_id` 字段进行数据级隔离（系统公有 / 部门 / 个人私有）。

认证方式：OAuth2 表单登录 + JWT Bearer Token。**未登录用户不可访问任何接口（401）**。

# 2. 角色定义

## 2.1 全局角色（Casbin）

| 角色 | 角色标识 | 说明 |
|---|---|---|
| 系统管理员 | `admin` | 穿透一切全局功能与项目级权限（列表可见全量、可管理，用于系统审计与保底兜底）。模型侧：可见全部配置**元数据**（归属人/模型名/状态等），但 URL/API Key **除本人私有配置外一律脱敏**，且**不可绑定使用他人私有模型**。 |
| 普通用户 | `user` | 系统的主体。可创建私有知识库、配置个人私有模型、使用系统公有/本部门模型。 |

## 2.2 项目内角色（成员表，数值越大权限越高）

| 档位 | 角色 | 权限说明 |
|---|---|---|
| 3 | `project_admin` | 全部：删除项目、成员与部门管理、**设置公开/私有（`publish`）** |
| 2 | `project_editor` | 读 + 写：上传/修改文档、对话问答（**不可变更公开/私有状态**） |
| 1 | `project_reader` | 仅只读：查看文档、对话问答 |

# 3. 知识库（项目）权限设计

## 3.1 默认私有规则

知识库字段 `is_private` 默认值为 **`true`（私有/非公开）**——当前代码已如此，无需数据迁移；本版落地重点是隐身的**服务端强制**：

- **私有状态（默认）**：只有 创建者 / 直连成员 / 授权部门 的用户能看到该知识库——**列表不返回（5.1 SQL 过滤）+ 详情读访问返回 404（5.2）**，两层共同构成"完全隐身"。
- **公开状态（手动开启）**：`is_private = false` 时所有登录用户均可在列表中看到并**只读**该知识库。"设为公开/私有"是 `project_admin` 专属动作（动作码 `publish`，档位 3），editor 不可变更可见性。

## 3.2 知识库创建与授权规则

1. **创建即拥有**：新建知识库后，创建者自动成为该知识库的 `project_admin`（档位 3）。
2. **显式授权**：`project_admin` 可添加其他用户或部门，并为其分配 `admin` / `editor` / `reader` 档位。
3. **保底规则**：移除成员或降级时，必须保证该知识库至少保留一个**激活的** `project_admin`（直连成员与部门授权来源均计入统计），防止知识库成为"孤儿"。
   - 仅统计 `is_active=true` 的用户；唯一 admin 被禁用/注销同样触发保底拦截。
   - 与 admin 穿透的关系：全局 admin 的 Casbin 穿透保证系统层面永远有人可管，业务层保底仅防"业务层无人可管"，二者不互相替代。

## 3.3 知识库权限矩阵

| 角色 / 状态 | 私有知识库（默认） | 公开知识库（手动开启） |
|---|---|---|
| 系统管理员(admin) | 穿透可见、可管理（列表全量 + 内容操作，用于审计与兜底） | 穿透可见、可管理 |
| project_admin | 所有权限 | 所有权限 |
| project_editor | 读 + 写 | 读 + 写 |
| project_reader | 只读 | 只读 |
| **其他登录用户** | **不可见、不可读、不可写（列表隐身，详情 404）** | **只读（可查看/问答，不可写）** |
| 未登录用户 | 401 不可访问 | 401 不可访问 |

> 补充：项目内成员档位不足时的访问返回 **403**（例如 editor 尝试删除）；仅"私有库 + 非成员"的**读**访问返回 **404**。

# 4. 模型管理权限设计

模型分为 **系统公有模型 / 部门模型 / 用户私有模型** 三类，通过 `scope` + `user_id` / `dept_id` 字段隔离（v3 只有公有/私有两类，v4 补全部门模型）。

## 4.1 模型归属与可见性

| 模型类型 | 归属 | 可见性与可用性 | 密钥(URL/API Key)保护 |
|---|---|---|---|
| **系统公有模型** | `scope=public`（`user_id` 为空） | 所有登录用户可见、可用。 | 后端脱敏（`mask_secrets`），前端不可见明文。 |
| **部门模型** | `scope=dept`（`dept_id`） | 归属部门成员可见、可用。 | 后端脱敏，前端不可见明文（密钥仅系统内部调用使用）。 |
| **用户私有模型** | `scope=user`（`user_id=本人`） | **仅创建者本人**可见、可用。 | 仅本人可见明文；**admin 可见元数据，但密钥一律脱敏**（信任基石：谁也拿不走用户的 Key）。 |

## 4.2 模型操作权限矩阵

| 操作 | 系统管理员 (admin) | 普通用户 (user) |
|---|---|---|
| **新增/修改/删除** 系统公有模型 | 是 | 否 |
| **设置** 系统默认公有模型 | 是 | 否 |
| **新增/修改/删除** 个人私有模型 | 否（不可越权操作他人数据） | **是（仅限 `user_id = 自己` 的数据）** |
| **绑定使用** 他人私有模型 | **否**（admin 不放行） | **否** |
| **测试** 模型连通性 | 是（测公有/部门/自己名下配置；**不可测他人私有**） | 是（测公有/部门/自己私有） |
| **查看** 模型配置列表 | 是（**全量元数据**；他人配置的 url/api_key 一律脱敏） | 是（公有 + 本部门 + 自己私有） |

> 补充安全要求：创建/修改私有模型时校验 `base_url`（协议白名单 http/https，可选域名黑名单），并记录审计日志——私有配置不允许成为无审计的内网探测通道。

## 4.3 模型调用兜底链

当用户发起问答或向量化请求时，模型选择逻辑如下：

```text
1. 用户个人偏好绑定的模型（自己的私有 / 本部门 / 系统公有）
   ↓ (若未绑定或已失效)
2. 系统默认公有模型 (scope=public 且 is_default=true 且 is_active=true)
   ↓ (若系统未配置或已禁用)
3. 返回"无可用模型"错误（不做进一步静默兜底）
```

补充规则（v4 新增）：

- **回退可感知**：发生"绑定模型 → 默认公共模型"回退时，响应（SSE 场景在首包 meta）必须提示"绑定的模型不可用，已回退系统公共模型"；
- **回退可关闭**：提供用户级开关"绑定模型不可用时直接报错，不回退"（默认开启回退）。用户选择私有模型往往意味着"数据不经系统服务商"，静默降级会改变数据流向且用户无感知；
- v3 中的"config.yaml 兜底"仅指系统默认公共模型的 seed 来源，不作为运行时第三级兜底。

# 5. 开发鉴权与查询规则

## 5.1 列表查询过滤（SQL 级拦截）

用户请求知识库列表时，后端必须拼接以下可见性条件（推荐 `EXISTS` 写法）：

```sql
WHERE (
    is_private = false  -- 公开库所有登录用户可见
    OR created_by = :current_user_id  -- 自己创建的
    OR EXISTS (SELECT 1 FROM project_member pm
               WHERE pm.project_id = project.id AND pm.user_id = :current_user_id)  -- 直连成员
    OR EXISTS (SELECT 1 FROM project_dept pd
               WHERE pd.project_id = project.id AND pd.dept_id IN (:user_dept_chain))  -- 部门授权(含祖级级联)
)
```

*注 1：系统管理员（admin）跳过此过滤，看到全量列表以便系统审计（与 2.1/3.3 一致）。*
*注 2：用户无部门时必须省略部门子句，不得生成 `IN ()` 非法 SQL。*
*注 3：部门链由用户所在部门的 `ancestors` 祖级链 + 自身部门构成，每请求查询一次并在 list/count 间复用。*

## 5.2 接口鉴权顺序

```text
1. 校验 JWT 登录态（401）
2. 校验全局菜单/按钮权限（Casbin enforce，403）
3. 若是模型接口：校验数据归属（scope=public / dept 命中 / user_id==self；admin 元数据可见但密钥脱敏）
4. 若是知识库接口：校验项目级档位（max(直连, 部门) >= 动作所需档位，403）
5. 校验公开/私有状态：私有库非成员 → 列表不返回；读接口返回 404（防存在性探测）；写接口返回 403
```

## 5.3 列表返回权限位 (`my_perms`)

列表接口需为每个知识库计算并返回当前用户的操作权限位，前端据此渲染 UI：

```json
{
  "id": "101",
  "name": "我的商业计划书",
  "is_private": true,
  "my_perms": {
    "read": true,
    "upload_doc": true,
    "update": true,
    "delete": false,
    "manage_member": false
  }
}
```

> 字段映射（前后端约定）：`upload_doc` ← 后端动作 `upload`；`manage_member` ← 后端动作 `invite/remove/manage`；其余同名。分页场景需批量计算（一次取当页 project_ids 批量查成员/部门授权表），禁止逐项目 N+1 查询。

# 6. 最终规则总结（半 To C 版 v4）

1. **隐私优先**：知识库默认私有，未授权用户在列表中完全看不到该知识库，直接访问详情返回 404。
2. **分享机制**：仅 `project_admin` 可将知识库设为"公开"（`publish` 动作），全员可见但仅限只读。
3. **创建者即 Owner**：新建知识库自动成为 `project_admin`。
4. **三档协作**：`admin`（管理）/ `editor`（写文档）/ `reader`（只读）。
5. **模型三类隔离**：公有 / 部门 / 个人私有（自己的 API Key）；admin 可见全量**元数据**用于运维，但密钥除本人私有配置外一律脱敏，且**不可绑定使用他人私有模型**。
6. **模型兜底**：优先用户绑定模型，其次系统默认公共模型；回退必须可感知，并提供"不回退直接报错"的用户开关。
7. **管理员边界**：admin 穿透项目权限用于管理与审计（列表全量、可管理）；模型侧只多"元数据可见"，不多"密钥可见"与"他人私有模型可用"。
8. **保底机制**：任何知识库必须至少保留一个**激活的** `project_admin`（直连或部门授权来源均计入）。
9. **未登录拦截**：系统不对外网匿名开放，所有接口必须携带 JWT（401 拦截）。
