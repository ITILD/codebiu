# 内存优化指南

> 背景：后端 `code/backend/server_py` 单进程启动后内存占用过高。
> 根因主要是 **启动链路 eager import 了全部业务模块**，且部分模块在 **import 时就加载 AI 模型 / 重型原生库**。
> 本指南先给定位方法，再给按收益排序的优化手段，最后附立即可做的清单。

## 1. 内存都花在哪了

### 1.1 启动链路：全模块 eager import

[app.py](../../../code/backend/server_py/src/app.py) 在顶层 import 了所有 module_*（module_ai、module_nlp、module_rag、module_agent、module_geometry 等），Python 的 import 是级联的——每个 controller 会拉起 service → dao → utils 的完整依赖链。任何一个 utils 顶层 import 了 torch/transformers，主进程就背上整个推理栈。

### 1.2 重型依赖清单（[pyproject.toml](../../../code/backend/server_py/pyproject.toml)）

| 类别 | 依赖 | 典型常驻内存 |
| :--- | :--- | :--- |
| LLM/Embedding | torch、transformers、sentence-transformers、peft | 数百 MB～数 GB（含模型权重） |
| OCR/视觉 | onnxruntime、opencv-contrib-python、ultralytics | 数百 MB |
| 语音 | sherpa-onnx(+core) | 数百 MB（含 TTS/ASR 模型） |
| NLP | spacy（zh_core_web_sm） | ~100 MB |
| 文档解析 | docling、pypdfium2、polars、pyarrow | 数百 MB |
| 向量库 | lancedb、pymilvus、pyarrow、sqlite-vec | 连接 + 数据缓存 |
| 其他 | playwright（浏览器进程另计）、neo4j driver、langchain 全家桶 | 数十～数百 MB |

### 1.3 import 时即执行加载的点（当前证据）

- [spacy_tokenizer.py:6](../../../code/backend/server_py/src/module_nlp/utils/tokenizer/spacy_tokenizer.py#L6)：模块顶层 `tokenizer = spacy.load("zh_core_web_sm")`，**且 import 时就跑了一段示例文本处理**。只要该模块被 import 链拉起，模型立即常驻。
- [loaders.py:9-16](../../../code/backend/server_py/src/module_ai/utils/llm/model_load/loaders.py#L9-L16)：顶层 `import torch` + `from transformers import ...`，import 即加载 torch 运行时（数百 MB）。
- [yolo/train.py:23](../../../code/backend/server_py/src/module_ai/utils/vision/yolo/train.py#L23)、[yolo/predict.py:23](../../../code/backend/server_py/src/module_ai/utils/vision/yolo/predict.py#L23)：顶层 `from ultralytics import YOLO`，连带加载 torch。
- [ocr/runtime.py:12](../../../code/backend/server_py/src/module_ai/utils/ocr/runtime.py#L12)：顶层 `from onnxruntime import ...`。
- [docling/base.py:14](../../../code/backend/server_py/src/module_office/utils/file_parase/docling/base.py#L14)、[docling/parsers/pdf.py:9-12](../../../code/backend/server_py/src/module_office/utils/file_parase/docling/parsers/pdf.py#L9-L12)：顶层 import docling。
- 模型实例化（sherpa TTS、YOLO、transformers）目前多为**类内/函数内按需加载**，方向正确，但被 eager import 抵消了收益。

## 2. 定位方法：先测量再优化

```bash
cd code/backend/server_py

# 1) 看各模块 import 耗时与顺序(间接反映 import 链)
$env:PYTHONPATH="src"; python -X importtime src/app.py 2> import.log

# 2) 用 memray 定位 import 阶段的内存分配(uv add --dev memray)
$env:PYTHONPATH="src"; python -m memray run src/app.py
memray flamegraph memray-src.app.py.<pid>.bin
```

- 火焰图里找 **import 阶段**（服务启动前）的分配大头，通常是 `torch/transformers/onnxruntime` 的原生库初始化。
- 运行期增长用 `tracemalloc` 快照对比，或直接访问已有的 `/main/status`（基于 psutil 的服务状态接口）观察 RSS 曲线。
- 判断某模块是否被主进程拉起：`python -c "import sys; ..."` 前置模拟，或直接在 import.log 中搜模块名。

## 3. 优化手段（按收益排序）

### 3.1 惰性导入重型模块（收益最大，不改架构）

原则：**controller → service 的链条只允许出现轻量依赖；torch/transformers/onnxruntime/spacy/docling 只允许出现在函数体内。**

```python
# 反例: 顶层 import, import 即加载
from module_ai.utils.vision.yolo.predict import YoloPredictor

# 正例: 使用时才加载
def get_yolo_predictor() -> "YoloPredictor":
    from module_ai.utils.vision.yolo.predict import YoloPredictor  # 函数内 import
    return YoloPredictor.get_instance()
```

- FastAPI 路由注册不依赖 utils 的顶层 import，函数内 import 对启动耗时也无影响（首次请求略慢，可接受）。
- 对 [spacy_tokenizer.py](../../../code/backend/server_py/src/module_nlp/utils/tokenizer/spacy_tokenizer.py) 这类顶层 `spacy.load`，改为 `get_tokenizer()` 惰性单例 + 删除 import 时的示例处理代码。
- 注意：不要用 `lru_cache` 包住异步/带参对象以外的重模型加载器以外的东西过多，模型加载器统一走"模块级 `_instance` + 双检锁"或项目已有的 dependencies 工厂模式（参考 [dependencies/status.py:3-5](../../../code/backend/server_py/src/module_main/dependencies/status.py#L3-L5) 的软单例写法）。

### 3.2 模型单例 + 显式生命周期

模型实例必须全局唯一、按需创建、可主动释放：

```python
class SherpaTTS:
    _instance = None

    @classmethod
    def get_instance(cls) -> "SherpaTTS":
        if cls._instance is None:
            cls._instance = cls()   # 首次调用才 OfflineTts(cfg)
        return cls._instance
```

- 同一份模型禁止在多个 service 中各加载一次（YOLO predict/train、OCR 各子模型、embedding 模型都要收敛到单例工厂）。
- 提供统一的 `release()`（del 模型引用 + `gc.collect()`），用于低峰卸载或切换模型。

### 3.3 进程拆分：主服务轻量化，重 AI 独立部署

最彻底的方案：把 module_ai / module_office(文档解析) 拆成独立 FastAPI 服务（独立进程、独立内存上限），主服务通过 HTTP/内网调用。

- 主服务（路由 + DB + RAG 编排）内存可降到几百 MB 量级。
- 重服务可单独重启/限流/漂移，不影响主服务可用性。
- 过渡方案：先用环境变量开关（如 `ENABLE_HEAVY_MODULES=false`）让 app.py 跳过 module_ai 的 import，验证收益后再拆分。

### 3.4 推理配置降档

- onnxruntime 会话限制线程与内存：`SessionOptions` 设置 `intra_op_num_threads`、`enable_mem_pattern=False` 可省数百 MB（见 [module_ai/config/ocr.py](../../../code/backend/server_py/src/module_ai/config/ocr.py) 已有配置位）。
- 优先使用 int8 量化 onnx 模型（sherpa、PaddleOCR 转 onnx），权重体积和常驻内存通常降 60%～75%。
- transformers 本地 LLM：用 `torch_dtype=torch.float16`（GPU）或 `bfloat16`，加载后可 `model.eval()` + 按需 `gradient_checkpointing` 无关内存项忽略；长对话注意 KV cache 的累积上限。

### 3.5 缓存与累积结构治理

- 项目已有 [ttl_cache](../../../code/backend/server_py/src/common/utils/cache/cache_ttl.py)（带 TTL 的方法缓存），新缓存一律用它或 `lru_cache(maxsize=N)`，**禁止无界 dict/list 当缓存**。
- 排查后台任务（[app_task.py](../../../code/backend/server_py/src/app_task.py)，celery `--pool=solo --concurrency=1`）与 SSE/WebSocket 会话中保存历史消息的结构，超过上限要落库或截断。
- langgraph checkpoint（postgres）保存的是状态而非内存，确认没有进程内重复缓存对话历史。

### 3.6 连接池与并发参数

- 数据库连接池（common/config/db.py）按实际并发设置 `pool_size`（如 5～10），不要默认拉满；每条连接在 asyncpg 侧约几 MB。
- httpx/aiohttp 客户端复用单例，避免每次请求新建连接池。
- uvicorn 单进程即可，不要盲目多 worker：每个 worker 都是完整 import 链，内存翻倍。

## 5. 长期约定

- 新增重型依赖前，先回答两个问题：**是否必须主进程加载？是否可以惰性加载？** 两者答案都为"是"时才允许顶层 import。
- code review 检查项：controller/service 禁止顶层 import AI 推理库；模型加载必须走单例工厂。
- 每个模块的 README/文档标注其重型依赖，便于评估部署内存预算。
